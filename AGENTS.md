# PawConnect – Agent Brief

Read this file before doing anything in this repository.

## 1. What this project is

- PawConnect is a **prototype** pet adoption web platform built by a 5-person university team (USYD PMGT5871 Project Planning, Group Assignment 2).
- The assignment assesses how the team applies **Scrum** (Jira backlog, sprints, ceremonies, evidence). The website is **not assessed for design, complexity or technical quality**. It exists only to prove that each user story marked Done in Jira was really delivered.
- A user story counts as Done only if (a) it is Done in Jira **and** (b) a screenshot of the working feature appears in the Sprint Review section of the report. So every feature must genuinely work against real (fictional) data. Never fake a feature with hard-coded output.
- Users: **Prospective adopters** (public, no login) and **Shelter staff** (one demo staff login).

## 2. Rules for the coding agent

1. **Build only what the current prompt asks for.** Each prompt names one Jira story (e.g. `PAW-12`) or one spike test. Do not implement other stories "while you are there", even if they are small. Building ahead breaks the team's sprint evidence.
2. **Keep it simple.** Plain HTML + CSS + vanilla JavaScript. No framework, no bundler, no build step. Minimal, clean styling is enough.
3. **One story = one small change set.** When done, suggest a commit message in the form `PAW-<number> <short summary>` (the team will use the real Jira key).
4. **After each change, list how to verify every acceptance criterion manually** (click path + expected result), so a teammate can test and screenshot it.
5. **Fictional data only.** Never add real names, phone numbers, emails or addresses. Use `example.com` emails.
6. **Database changes go in a new SQL file** under `supabase/migrations/` (e.g. `002_add_shelter_page.sql`). Say clearly that a human must run it in the Supabase SQL Editor. Do not silently assume schema changes exist.
7. **Secrets:** the Supabase *anon* key may live in `config.js` (it is public by design; security comes from Row Level Security). The *service_role* key must never appear in the repo or in front-end code.
8. If a story's acceptance criteria are ambiguous or conflict with this brief, **stop and ask** instead of guessing.
9. UI text in English (Australian spelling).

## 4. Data model (see `supabase/schema.sql`)

- `shelters(shelter_id, shelter_name, suburb, demo_phone, description)`
- `pets(pet_id, shelter_id, name, animal_type, breed, age_years, sex, availability, description, photo_url)`
  - `animal_type`: Dog | Cat | Rabbit | Other
  - `availability`: Available | On Hold | Adopted
- `applications(application_id, pet_id, applicant_demo_name, demo_email, reason, application_status, submitted_at)`
  - `application_id` is generated by the database, format `APP-1004`, `APP-1005`, …
  - `application_status`: Pending | Under Review | Approved | Rejected (new applications are always Pending)

Access rules (enforced by RLS and functions in `schema.sql`):

- Public (anon) can **read** shelters and pets.
- Public **cannot read or update the applications table directly.** They submit via `rpc('submit_application', …)` which returns the new `application_id`, and look up a single application via `rpc('track_application', { p_application_id })`, which returns only ID, pet name, status and submitted time.
- Signed-in staff (`authenticated`) can read and update applications, and insert/update pets.

## 5. Page ↔ story map (draft – Jira is the source of truth)

| Page | Epic | Draft stories |
|---|---|---|
| index.html | E1 Platform Experience | Homepage, adoption process guide, privacy notice, mobile layout |
| pets.html, pet.html | E3 Pet Discovery | Listing, profile, list→profile link, filter by type, filter by availability; shelter info (E1) |
| apply.html, confirm.html | E4 Adoption Application | Start from profile, enter details, required-field validation, submit + confirmation |
| track.html | E2 Application Tracking | Search by reference, view status, status explanations, not-found message |
| staff*.html | E5 Shelter Management | View applications, view detail + pet, update status, add pet, update availability |

Story wording, acceptance criteria and sprint scope live in Jira and will be pasted into each prompt.

## 6. Definition of Done (for code)

A change is ready for the team's Testing column when: every acceptance criterion in the prompt works against live Supabase data on the deployed GitHub Pages site, there are no console errors on the affected pages, and the manual verification steps are written down.
